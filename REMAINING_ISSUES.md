# Inklly Production Readiness — Open Work

**Status:** Not ready for production; development and verification continue.
**Updated:** 2026-10-29

## Current verification

- `npm run build` passes all workspaces from the clean shared-package build output after fixing dependency order. Route-level loading keeps the initial Vite 6.4.5 JavaScript bundle at 215.91 kB minified (61.11 kB gzip); PDF rendering is a separate 483.94 kB chunk and no oversized-chunk warning remains.
- `npm run build` and `npm test` pass locally (242 tests: database 15, shared 15, agent 14, server 198). Two `npm audit --audit-level=high` attempts timed out reaching npm's advisory service, so current dependency status is unverified. These are local unit/integration tests, not live provider, webhook destination, storage, browser or hardware verification. `npm run lint` is not configured.
- Agent command polling is now gated on merchant release (`READY_FOR_PRINT`/`IN_PROGRESS`) and verified online payment. The local worker catches unexpected execution exceptions, preserves ambiguous output as `OUTPUT_UNCERTAIN`, serializes queue cycles, and drains in-flight work during shutdown. Printer dispatch also requires a fresh heartbeat; stale/unknown queues are not dispatchable. Merchant dashboard revenue now comes from the customer-payment ledger rather than order status; these behaviors have regression coverage.
- Physical printing remains disabled by default and is not verified on hardware. The executor requires an exact discovered queue match, applies supported range/copies/color/duplex/orientation/paper/collation settings, rejects unsupported options, and reports `SUBMITTED_TO_SPOOLER` instead of claiming physical output. Printer ownership is scoped to the reporting agent, and the Orders UI allows explicit queue selection. Downloads are origin/path restricted, redirect-blocked, bounded to 35 MiB, content-checked, and written to random private temporary paths; interrupted dispatched jobs are reported as `OUTPUT_UNCERTAIN` and never automatically retried. Driver capability/status fidelity and hardware verification remain open. Keep `INKLLY_ENABLE_PHYSICAL_PRINTING=false` until these gates are closed.
- Subscription usage metering appends one idempotent, mutation-protected event when a shop confirms complete physical output. Sides are computed from server-stored page counts, selected page ranges, and copy counts; `GET /api/v1/subscriptions/usage` reports the organization’s current period. Platform billing admins can set organization-specific monthly base/per-side rates with effective dates and issue immutable, idempotent monthly statements. Owners can read their own statements. Statements are manual-pending and before tax; no payment or ledger entry is created. Automated subscription collection, tax calculation, quota enforcement, and live PostgreSQL migration verification remain open.
- Refund requests reserve refundable payment balance. A pending request can be rejected transactionally, freeing the reservation and recording an audit entry without a ledger/payment mutation. Provider refund approval and money movement remain unavailable.
- Merchant authentication checks persisted account activity, current shop membership role/permissions, and current shop activity for each authenticated request; an inactive shop is denied even while an old session remains valid. Regression coverage checks dashboard and printer access. Global platform permission lifecycle and broader membership-administration workflows still need separate review.
- Agent heartbeat payloads are now validated completely before persistence: status, integer counters, cache-health boolean, and every optional printer inventory record must have valid bounded values. A malformed heartbeat no longer advances the online timestamp or partially replaces printer inventory. Merchant rate list/update calls now surface HTTP errors, and a partial settings save is shown as a failure. These paths are covered in the passing API suite.
- Developer webhook secrets are encrypted at rest with purpose-bound AES-256-GCM, with legacy plaintext rows migrated at server startup. Local code now persists `order.created`, `order.status_changed`, and `payment.succeeded` events and deliveries transactionally; an HTTPS worker signs timestamped HMAC-SHA256 bodies, rejects any non-public DNS answer, pins the chosen public IP, retries with bounded backoff, and exposes tenant-scoped attempt history. Owner UI supports destination creation, one-time secret reveal, rotation, and revocation. External API access remains disabled by default. Hosted endpoint delivery and production network behavior remain unverified; historical replay, additional event types, and live operational monitoring remain open.
- Platform tenant onboarding and merchant staff provisioning now create durable records transactionally and return expiring, hashed, single-use setup links. Staff remain inactive until they set a strong password, and selected preset permissions are preserved. SQLite tests cover both flows; the PostgreSQL migration still needs live verification. Invitations are shown once in the authenticated UI; outbound email delivery is not configured. Admin incident handling, runtime configuration, and agent-build downloads still contain local-only or unavailable behavior.
- Merchant `GET /orders` supports tenant-scoped status filtering, search, allowlisted sorting, and pagination; the Orders screen uses those controls. Dashboard refresh uses grouped order counts and a five-order recent window. Order status transitions lock and revalidate the current row in a transaction. Printer status is heartbeat-derived and dispatch rejects stale/unknown queues. Rate-rule writes reject printer IDs outside the authenticated shop.
- Merchant vault now uploads inspected PDF/JPEG/PNG files into private storage, lists/streams/deletes them by shop, and persists category metadata; cleanup preserves vault objects and shared order uploads until no active order references remain. Local tests cover tenant denial and retention. Vault objects remain until staff delete them; approve and publish a long-term retention/privacy policy before production use. Live Supabase storage and PostgreSQL behavior remain unverified.
- Print-file deletion now coordinates with order creation via an owner-token lease and a five-minute recovery window. A 60-second storage timeout bounds active claims; server submission returns 409 if purge already claimed the file. Migration v17 and local API/concurrency coverage pass, but the migration and Supabase deletion are not verified on the production database/bucket.
- Merchant `PUT /settings` now enforces `settings:manage`; the API contract text and regression cover an unprivileged manager denial and an authorized staff update.
- Platform ledger uses stable cursor pagination, the console can load additional rows, and CSV export retrieves every page across domains. A 205-row regression confirms no omissions or duplicates.
- Merchant printer-profile creation now rejects malformed names, capability values, trays, paper-size lists, and duplicate default trays; it ignores client-supplied IDs and online status. Shared quotes reject malformed ranges and cap files, pages, copies, and total integer Paise. Platform audit logs now support stable cursor paging, load-older UI, and full-history formula-safe CSV export. Incident workflow and persistent feature-flag/runtime management remain open.
- Public customer quote, upload, and order endpoints return HTTP 400 for null or structurally invalid request bodies; malformed JSON is also mapped to a client error. Regression checks cover these cases and a stable staff-revocation audit lookup.
- Code through `dc219dc` is pushed to GitHub and the Vercel site responds HTTP 200. Latest live Render checks still show health without `revision` and a seven-path OpenAPI document. The source contains the required startup checks for `STORAGE_DRIVER=supabase`, an HTTPS Supabase URL, service-role key, and private bucket, but live dashboard configuration is not accessible here.
- No Render CLI, deploy token/hook, deployment tool, or browser dashboard session is available here to trigger a backend deployment. Production tenant state remains unverified.
- WhatsApp Cloud API onboarding and delivery remain unavailable. The UI now says so directly, and API writes/pairing requests return HTTP 503 without persisting fake pairing state; Meta onboarding, encrypted credential storage, webhooks, and message delivery remain to be built.
- Ordinary JSON parsing is capped at 1 MiB. Customer uploads have shared atomic per-IP limits (30/minute and 1,000/day by default) before the larger upload parser, in addition to a per-process concurrency cap. Merchant vault uploads are authorized before parsing and use the concurrency cap; shared vault limits and production-like load validation remain open. Website-enquiry rate limiting is still process-local, so a shared edge/WAF limit is needed when scaling.
- Public enquiries are now durably stored and shown in the authenticated platform console. No email/WhatsApp notification is configured, and an approved retention period for enquiry contact details/message text is still required. Rate limiting is process-local; a shared edge/WAF limit is needed before horizontal scaling.
- Developer API keys are shop-bound and require `ENABLE_EXTERNAL_API_ACCESS=true`; authentication enforces environment, expiry, revocation, active owner membership, and least-privilege scopes. Local SQLite tests cover these checks; live PostgreSQL migration/runtime behavior remains unverified.
- Platform plan-status/tier updates now validate the target, return 404 for missing organizations, and record privileged audit entries atomically. The admin console no longer presents fake installer downloads, sample incidents, browser-only runtime saves, or fabricated tenant hardware; installer distribution, persistent incident management, and audited runtime configuration remain unavailable. Refund requests reserve balance under a transaction lock; concurrent partial-refund tests cover the local database path.
- Per-file instructions now persist to merchant-visible print options with 500-character server validation. The PDF editor shows the actual uploaded first page and labels crop/rotation/filter controls as preview-only; these edits still do not change the stored print file.
- Platform-admin permissions use owner-only management, separate persisted grants, per-request refresh, and audit events. Migration v16 and local tests cover grant/revoke behavior; provisioning of new platform-admin accounts and live PostgreSQL migration/runtime checks remain release follow-up.
- Ledger entries are append-only under SQLite and PostgreSQL startup migrations, and a unique provider-transaction index prevents duplicate ledger postings. Migration v10 checks for existing duplicate provider transaction IDs and fails closed for operator reconciliation; production Supabase has not been inspected or migrated.

## Product scope choices

- India launch uses Razorpay, with each shop entering its own credentials.
- Hybrid shop subscription plus usage is planned; pilot base and per-printed-side prices remain configurable.
- Customer files are intended to be deleted 24 hours after order completion.
- QR ordering and print-shop pickup are in scope. Kiosk/ATM, franchise, space-partner, and delivery workflows are excluded.
- WhatsApp outbound messaging requires configured Meta Business credentials and verified end-to-end behavior.
