# Inklly Production Readiness — Open Work

**Status:** Not ready for production; development and verification continue.
**Updated:** 2026-10-30

## Current verification

- `npm run build` passes all workspaces. PDF rendering is a separate 484.31 kB lazy-loaded chunk and no oversized-chunk warning remains.
- `npm run build` and `npm test` pass locally (289 tests: database 24, shared 16, agent 15, server 221, web 13). Organization/subscription listings are bounded, and enquiry limits use shared persistent counters. Customer tracking stops polling after final outcomes; Supabase API operations are timeout-bounded; terminal agent rows erase document locators and print options. Two earlier `npm audit --audit-level=high` attempts timed out reaching npm's advisory service, so current dependency status is unverified. These are local tests, not live provider, Supabase, browser or hardware verification. `npm run lint` is not configured.
- Agent command polling is now gated on merchant release (`READY_FOR_PRINT`/`IN_PROGRESS`) and verified online payment. The local worker catches unexpected execution exceptions, preserves ambiguous output as `OUTPUT_UNCERTAIN`, serializes queue cycles, and drains in-flight work during shutdown. Printer dispatch also requires a fresh heartbeat; stale/unknown queues are not dispatchable. Merchant dashboard revenue now comes from the customer-payment ledger rather than order status; these behaviors have regression coverage.
- Physical printing remains disabled by default and is not verified on hardware. The executor requires an exact discovered queue match, applies supported range/copies/color/duplex/orientation/paper/collation settings, rejects unsupported options, and reports `SUBMITTED_TO_SPOOLER` instead of claiming physical output. Printer ownership is scoped to the reporting agent, and the Orders UI allows explicit queue selection. Downloads are origin/path restricted, redirect-blocked, bounded to 35 MiB, content-checked, and written to random private temporary paths; interrupted dispatched jobs are reported as `OUTPUT_UNCERTAIN` and never automatically retried. Driver capability/status fidelity and hardware verification remain open. Keep `INKLLY_ENABLE_PHYSICAL_PRINTING=false` until these gates are closed.
- Subscription usage metering appends one idempotent, mutation-protected event when a shop confirms complete physical output. Platform billing admins can configure effective-dated monthly base/per-side tariffs and issue immutable statements; statements are manual-pending and before tax. A platform-owned Razorpay monthly checkout, signed webhook, capture verification, and pending-attempt reconciliation are implemented locally, but a live sandbox round trip is still unverified. Automatic renewals, usage-invoice collection, tax, quota enforcement, and live PostgreSQL migration verification remain open.
- Conversion-credit purchases and document-conversion usage are not implemented. The merchant screen now shows billing/print usage instead of mock balances; the credit top-up endpoint returns 503 until a real provider-backed flow is available.
- Merchant payouts are unavailable because customer payments settle directly to each shop; referral rewards are out of pilot scope. The merchant UI now states both limits and has no sample withdrawal/referral balances or simulated success handlers.
- Refunds now support shop-owned Razorpay processing with stable provider idempotency, signed refund webhook reconciliation, and ledger posting only after provider confirmation. Cash refunds require explicit return confirmation and an audit note. Credential rotation/removal is serialized against checkout/refund reservations and blocked while Razorpay payments or refunds are unresolved when a complete configuration is already present; incomplete configuration can be repaired so a stuck refund can resume. Local provider-mocked regressions cover pending-to-processed, duplicate and out-of-order events, timeout retry identity, credential preservation, and incomplete-setup recovery. Live Razorpay sandbox/webhook and production PostgreSQL behavior remain unverified.
- Razorpay credential status, save, test, and removal now require the authenticated persisted organization owner for the active shop; platform-owner support access cannot select another tenant and change its credentials. Successful save/removal writes a secret-free audit entry atomically. The current API regression verifies owner success, audit contents, and denial of platform-owner status/save/test/remove attempts.
- Merchant authentication checks persisted account activity, current shop membership role/permissions, and current shop activity for each authenticated request; an inactive shop is denied even while an old session remains valid. Regression coverage checks dashboard and printer access. Global platform permission lifecycle and broader membership-administration workflows still need separate review.
- Agent heartbeat payloads are now validated completely before persistence: status, integer counters, cache-health boolean, and every optional printer inventory record must have valid bounded values. A malformed heartbeat no longer advances the online timestamp or partially replaces printer inventory. Merchant rate list/update calls now surface HTTP errors, and a partial settings save is shown as a failure. These paths are covered in the passing API suite.
- Developer webhook secrets are encrypted at rest with purpose-bound AES-256-GCM, with legacy plaintext rows migrated at server startup. Local code now persists `order.created`, `order.status_changed`, and `payment.succeeded` events and deliveries transactionally; an HTTPS worker signs timestamped HMAC-SHA256 bodies, rejects any non-public DNS answer, pins the chosen public IP, retries with bounded backoff, and exposes tenant-scoped attempt history. Owner UI supports destination creation, one-time secret reveal, rotation, and revocation. External API access remains disabled by default. Hosted endpoint delivery and production network behavior remain unverified; historical replay, additional event types, and live operational monitoring remain open.
- Platform tenant onboarding and merchant staff provisioning now create durable records transactionally and return expiring, hashed, single-use setup links. Staff remain inactive until they set a strong password, and selected preset permissions are preserved. SQLite tests cover both flows; the PostgreSQL migration still needs live verification. Invitations are shown once in the authenticated UI; outbound email delivery is not configured. Admin incident handling, runtime configuration, and agent-build downloads still contain local-only or unavailable behavior.
- Merchant `GET /orders` supports tenant-scoped status filtering, search, allowlisted sorting, and pagination; the Orders screen uses those controls. Dashboard refresh uses grouped order counts and a five-order recent window. Order status transitions lock and revalidate the current row in a transaction. Printer status is heartbeat-derived; dispatch checks each file’s saved color, duplex, and paper-size options against the selected printer’s saved capabilities and the agent’s supported modes and rejects unsupported or unverified combinations before job assignment. Inventory retains a configured capability profile only when queue name and driver name match. Rate-rule writes reject printer IDs outside the authenticated shop.
- Merchant vault uploads inspected PDF/JPEG/PNG files into private storage, lists them with bounded tenant-scoped cursor pagination, streams/deletes them by shop, and persists category metadata; deletion tombstones are hidden and retried by a bounded worker, while shared order-file references preserve the object. Local tests cover tenant denial, cursor paging and retry recovery. Vault objects remain until staff delete them; approve and publish a long-term retention/privacy policy before production use. Live Supabase storage and PostgreSQL behavior remain unverified.
- Print-file deletion now coordinates with order creation via an owner-token lease and a five-minute recovery window. A 60-second storage timeout bounds active claims; server submission returns 409 if purge already claimed the file. Migration v17 and local API/concurrency coverage pass, but the migration and Supabase deletion are not verified on the production database/bucket.

Shared quotes reject malformed ranges and cap files, pages, copies, and total integer Paise. ## Product scope choices

- India launch uses Razorpay, with each shop entering its own credentials.
- Hybrid shop subscription plus usage is planned; pilot base and per-printed-side prices remain configurable.
- Customer files are intended to be deleted 24 hours after order completion.
- QR ordering and print-shop pickup are in scope. Kiosk/ATM, franchise, space-partner, and delivery workflows are excluded.
- WhatsApp outbound messaging requires configured Meta Business credentials and verified end-to-end behavior.
