# Inklly implementation status

**Snapshot:** 2026-10-30 (local source; not a production-readiness claim)

Use `BUILD_AND_TEST_RESULTS.md` for the latest executed checks and `REMAINING_ISSUES.md` for release blockers. Historical phase checklists were removed because several previously marked “complete” features were UI simulations or unavailable integrations.

## Working in source with regression coverage

- **Customer ordering:** shop lookup, private upload path, server-side file inspection, quote generation in integer Paise, stale quote confirmation, order persistence, and idempotent retry when the client supplies a stable key.
- **Accepted pricing and rate integrity:** order rows persist the calculated quote plus the exact rate and discount rules accepted at submission. Rate-rule updates use database uniqueness keys and atomic upserts so concurrent writes cannot create ambiguous prices. Existing duplicate pricing keys fail migration for manual reconciliation.
- **Merchant price management:** shop-wide print-side rates remain integer Paise. The merchant can persist one threshold bulk discount and A4 additional-copy rates; API writes are atomic and audited, and enabled additional-copy rates cannot exceed normal prices. Migration v23 enforces unique rule keys and fails closed on duplicate legacy data. Collage, merge, ID-card and photo-specific rates remain unavailable.
- **Agent concurrency:** local queue items are atomically claimed before spooler execution, so multiple processes sharing one queue cannot both submit the same pending job.
- **Merchant API:** signed persisted sessions, active-user/current-membership/current-shop checks (inactive shops are denied), route permissions, tenant-scoped order search/filter/sort/pagination, private order-file authorization, rate-rule printer ownership, and order status/dispatch rules. Order detail, status, dispatch, and reconciliation resolve by authenticated shop; foreign order IDs/numbers return the same 404 as missing records. Legacy order arrays cap at 100 and expose continuation metadata in headers; explicit paginated response bodies are unchanged.
- **Shop settings:** profile and operational settings now validate exact supported fields/types/enums and persist through the merchant settings route used by the UI; malformed truthy strings and unknown keys are rejected.
- **Shop settings authorization:** updates require the current persisted `settings:manage` permission; the API test confirms a manager without it is denied and a staff member with it can update settings. Platform administrators are explicitly denied from merchant routes so platform grants cannot be combined with a caller-selected `shopId`; platform-owner support access remains covered.
- **Account security:** merchant account profile name/phone updates persist through authenticated `PUT /auth/me` and are audited. `PUT /auth/password` verifies the current password, enforces a strong replacement, revokes other active sessions, and keeps the current session. The UI no longer displays sample identities or a hardcoded password.
- **Merchant dashboard:** status counts and recent orders come from tenant-scoped database queries; it no longer hydrates the complete order history to render its overview. Revenue is read from the payment ledger, not inferred from order state.
- **Staff and onboarding:** owner-created shop staff and platform-created tenant owners receive hashed single-use activation tokens; staff remain inactive until password setup.
- **Printer/agent safety:** agent-owned printer inventory, heartbeat freshness, exact matching of saved capability profiles to agent-reported queue identity, and per-file color/duplex/paper-size validation before dispatch are covered by local tests. The customer portal hides print modes the current agent cannot apply and rejects incompatible quotes before order submission. Incompatible jobs remain unassigned and keep their original order state. Dispatch to shop-owned queues, inactive-shop agent revocation, local durable outcome reporting, replay-safe dispatch IDs, and `OUTPUT_UNCERTAIN` handling are covered by local tests. Migration v24 stores the agent's explicit physical-printing readiness; the merchant API refuses job assignment and polling unless an active paired agent reports `physicalPrintingEnabled: true`. Legacy agents default to disabled. The agent loopback endpoints are read-only and validate host/origin.
- **Platform permissions:** platform admin grants are stored separately from merchant memberships; owners can view and replace grants through owner-only APIs and the admin console. Successful changes are audited, and middleware reloads permissions for every request so an existing session cannot retain revoked access. SQLite migration and API tests cover grant, denial, invalid grants, owner-only management, and revocation. Live PostgreSQL behavior remains unverified.
- **Payments and secrets:** Razorpay checkout uses shop credentials; payment verification validates provider records and webhook signatures. Razorpay and developer webhook secrets are encrypted at rest and omitted from ordinary API responses.
- **Razorpay credential access:** payment credential status, save, test, and removal require the authenticated persisted organization owner for the active shop. Successful save/removal and their non-secret metadata are audited atomically with the change; a platform-owner support bypass cannot rotate another shop's keys.
- **Merchant setup checklist:** each setup row now reports its actual ready, loading, optional, or attention state. Printer status remains explicitly unverified until supported hardware is validated, cash-only shops are not forced to configure Razorpay, and rows are keyboard-accessible navigation controls.
- **Developer webhooks:** order-created, order-status, and payment-success events enter the persistent outbox in their source transaction. Signed HTTPS delivery uses HMAC-SHA256, DNS-pinned public IPs, a bounded retry policy, attempt history, and owner controls for one-time secret display, rotation, and revocation. The developer portal separates synthetic preview from actual persisted delivery history.
- **Private files:** production refuses local-disk storage; upload concurrency is bounded, storage is private, and customer-order cleanup preserves objects referenced by any active order or vault document. Once all orders sharing a key are eligible, one removal expires every order reference. Merchant vault upload/download/delete use private storage and tenant-scoped metadata; listing is bounded to 100 records with cursor pagination, and delete uses hidden tombstones plus a bounded retry worker. Live PostgreSQL/Supabase behavior remains unverified.
- **Platform agent fleet:** the admin console refreshes persisted server inventory and makes no active-poll claim. The API counts printers as currently online only while their owning agent heartbeat is fresh; stale counts are labelled as last reported. Local API tests cover stale-agent printer reporting; live agent behavior is unverified.
- **Customer portal studios:** ID-card and passport-photo availability persists in shop portal settings and controls whether those modes appear to customers; both default off. Persistence and API contract are tested, but customer browser and resulting print outputs remain unverified.
- **Request parsing:** ordinary JSON requests are capped at 1 MiB. The two base64 file-upload routes have a shared pre-parser concurrency cap; vault uploads pass persisted session, tenant, subscription, and permission checks before large-body parsing.
- **Print confirmation:** agents can report spooler submission or uncertain output, but cannot attest printed pages. An authorized merchant must physically inspect output, confirm it with a reason, and the server records an audit event before an order becomes collectible.
- **Print output and cash collection:** merchant staff reconcile output per file/print job; partial confirmation keeps the order in progress and does not meter usage. Collection requires every print job to be physically confirmed and `READY_FOR_COLLECTION`. Generic order status updates cannot mark an unpaid order collected. The cash payment route transactionally writes the payment, ledger entry, order transition, and webhook event. Concurrent retries return the original result without duplicate records. API and end-to-end regressions cover partial reconciliation, metering, early rejection, and collection.
- **Merchant pickup and usage:** merchant cash collection is available only for a print-complete, collectible order. Owner billing view reads organization-scoped, operator-confirmed selected-page-times-copy usage. Usage statements remain manual-pending and do not collect charges.
- **Conversion credits:** the merchant workspace now labels the surface `Billing & usage` and shows the real print-side statements. The previous dormant mock top-up panel and invented balances were removed; the API stays unavailable until a real payment/usage workflow exists and tests verify a rejected purchase does not change ledger balance.
- **Pilot statements:** platform billing admins can set append-only organization tariffs effective by calendar month and issue idempotent immutable monthly statements from confirmed printed-side usage. Owners can read only their organization's statements. Statements remain manual-pending, before tax, and do not create payment or ledger entries.
- **Refunds:** supports shop-owned Razorpay refund requests, stable idempotency keys, provider status reconciliation through signed refund webhooks, and ledger posting only after provider confirmation. Cash refunds require explicit return confirmation and an audit note. Live provider and hosted PostgreSQL behavior remain unverified.
- **Merchant/public copy:** fixed plan prices and quotas, unsupported printer controls, and unconditional payment/privacy claims were removed or qualified. Marketing labels illustrative order data, Razorpay availability is described as shop-configured, and legal copy no longer promises unimplemented subscription or instant print refunds.
- **Platform data:** tenant onboarding, persisted agent fleet status, retention operations, financial summaries, tenant status updates, invoice-only pilot billing, and monthly subscription checkout/reconciliation use backend data. Incident intake, runtime configuration, signed installer distribution, automatic recurring charges, and quota enforcement remain incomplete; the console labels unavailable workflows.
- **Platform ledger:** cursor pagination uses stable `(created_at, id)` ordering, the table supports loading further pages, and CSV export fetches every page across all domains. A 205-row regression checks complete traversal without duplicates.
- **Customer instructions and document editing:** per-file instructions are limited to 500 characters, stored with persisted print options, and surfaced in the merchant order queue. Supported PDF crop/rotation and image adjustments are applied to a replacement file; it becomes active only after a private upload succeeds. Failed uploads leave the original untouched.
- **Print-file concurrency:** migration v17 adds lifecycle claims for SQLite and PostgreSQL. A five-minute token lease prevents deletion/order-creation races and recovers abandoned cleanup claims; storage deletion is bounded to 60 seconds, and customer order submission returns HTTP 409 if cleanup already claimed the object. Local migration, API, and concurrency tests cover the behavior; live PostgreSQL rollout remains unverified.

## Incomplete or unverified

- Source validates printer capability profiles, bounds shared quote calculations, provides stable cursor-based platform audit pagination and complete formula-safe CSV export, returns safe 400 errors for malformed public customer request bodies, applies database-backed upload quotas, and hides foreign-order existence through shop-scoped lookups. Vercel's latest bundle contents have not been reverified after recent pushes. Render's health omits `revision`; its live OpenAPI response still has only 7 paths and no payments, refunds, or current subscription/billing operations; an earlier probe found unauthenticated developer-key access returned 200 instead of the current source's 401. The source OpenAPI spec now documents shop payment and refund workflows.
- PostgreSQL migration/startup against the live production project and Supabase private bucket behavior remain unverified.
- Shop Razorpay checkout and the new platform monthly checkout have not been verified against live sandbox credentials/webhooks. Automatic renewals, usage-invoice collection, refunds/reconciliation against provider statements, tax calculation, and quota enforcement remain incomplete. Invoice-only hybrid usage billing does not collect money.
- Database migrations now install append-only ledger triggers and a unique provider-transaction index; local SQLite tests cover immutability, compensating entries, and duplicate rejection. Live Supabase migration, pre-existing duplicate review, platform support boundaries outside payment-credential controls, and complete reconciliation remain open.
- The merchant vault upload workflow supports inspected PDF/JPEG/PNG files, shop-owned categories, private downloads and deletion. Vault files are excluded from temporary order-file retention and remain until staff delete them; live Supabase behavior and approved long-term retention/privacy policy remain unverified.
- WhatsApp UI and setup routes report unavailable; real Meta onboarding, secure account lifecycle, inbound customer intake, and outbound messages are not implemented. Merchant message-template settings load and persist the supported GREETING and ORDER_READY text through the authenticated API, but do not send messages. Supported print modes and paper sizes are managed in persisted Customer Portal settings.
- Shop-bound API keys authenticate merchant business routes only when `ENABLE_EXTERNAL_API_ACCESS=true`, with environment, expiry, revocation, active membership, and least-privilege scope checks. Webhook delivery has local code and test coverage as described above; external API access is disabled by default, and hosted dispatch, replay controls, more event types, and full operational monitoring remain unverified or incomplete.
- Platform incident handling and mutable runtime configuration require durable, audited backend services. Subscription plan changes and quota enforcement are incomplete.
- A signed, verified desktop installer is unavailable. The agent refuses physical printing by default; no supported printer has been verified end to end.
- Customer uploads now use database-backed shared per-IP minute/day rate limits; shared limits for other public endpoints, browser-level visual testing, production load testing, backup/restore drills, monitoring, legal/privacy review, and password-reset email recovery remain release work.

## Product decisions already set

- India pilot: Razorpay, with each shop entering its own Key ID, API Secret, and webhook secret.
- Hybrid subscription plus usage is planned; base and per-successfully-printed-side rates remain configurable for the pilot.
- Customer print files are intended to be deleted 24 hours after order completion.
- Countertop QR and print-shop pickup are in scope; kiosk/ATM, franchise, delivery, and space-sharing models are excluded.
